The Operational Challenge

Insurance brokers in Kenya run on paperwork — KYC documents, claim forms and onboarding paperwork must be collected before a policy is bound or a claim paid. Today that chasing is manual: WhatsApp, SMS, email and spreadsheets in separate places, with no single source of truth.

The workflow’s purpose. Document chasing automation: a broker opens a case, the system sends the client a secure, tokenised upload link on their preferred channel, tracks responses, and flags anything still open after seven days to an exception queue for senior review. The broker decides; the system nudges and tracks.

Why manual chasing fails

Failure modes from discovery conversations with brokers, not assumptions:

  • Understanding Clients don’t understand what is needed — requests are incomplete or confusing.
  • Submission Documents are hard to submit — no mobile-friendly upload path, no app installation.
  • Trust Clients distrust upload links; prefer WhatsApp or email instead.
  • Tracking Brokers lose track of who owes what; follow-ups forgotten across disconnected channels.
  • Parties Client, broker, insurer and adjuster share responsibility, no shared status view.
  • Escalation Cases overdue >7 days have no path to a senior broker.

No revenue figures, conversion rates or client counts are claimed — a capability demonstration, not a delivered deployment.

Scope note. Document chasing only — payment reconciliation, automated underwriting and policy issuance are explicitly out of scope (Deliverable F).

The System Architecture

The system is n8n workflow WB-08 — Document Chasing Escalation, a multi-step workflow with sub-workflow triggers, conditional routing by escalation day, and integrations across Gmail, Google Sheets and HTTP webhooks. Every step below is taken from the real workflow definition (synthetic demo data; no live credentials).

StepWhat happens
1Document Chasing TriggerEntry from Chain 4 ops hub when verification is partial/invalid (Day 0). Also a daily 09:00 schedule trigger scans for overdue chases.
2Normalize New ChaseSet node normalises client details, missing fields, chase start date, escalation stage, consent and insurer / adjuster contacts.
3Gmail — Day 0 Secure Upload LinkSends the client a personalised, tokenised upload link listing exactly which documents are missing, why each is needed and the deadline. ODPC consent logged at first touch.
4Notify Insurer / Loss AdjusterHTTP POST webhook notifies insurer and loss adjuster (multi-party alignment — all parties see shared milestone status).
5Log ODPC Consent + Update TrackerLogs consent channel and date; appends a chase record to the Google Sheets document tracker.
6Daily Scan · Filter PendingReads the tracker; filters chases that are pending and not yet verified.
7Switch — Escalation DayConditional router by days since chase: +2 friendly nudge, +4 formal reminder, +7 phone-call task, renewals at 60/30/7/3 days, nothing due otherwise.
8Phone Task + Exception QueueDay +7 creates a broker phone-call task; >7 days with no response creates an exception queue entry (severity high, 24h SLA, recommended action).
9Update Tracker StageWrites escalation stage, last contact channel and status back to the tracker sheet; errors are logged rather than dropped.

Decision logic — conditional routing by escalation day

  • Day +2 Gmail friendly reminder · stage advanced · tracker updated.
  • Day +4 Gmail formal reminder · stage advanced · tracker updated.
  • Day +7 Broker phone-call task · exception queue entry, 24-hour SLA.
  • Renewals Separate cadence: 60 / 30 / 7 / 3 days before policy expiry.
  • Stop condition Escalation stops as soon as documents are verified.
Architecture note. Integrations (Gmail, Google Sheets, insurer/adjuster webhooks) require the buyer’s own n8n instance and credentials — configured at handover, not pre-connected to any live account.

Execution and Handover

Outputs produced

  • Upload link Tokenised, mobile-friendly client upload link per case — no app installation required.
  • Tracker record Chase record in Google Sheets: client, policy, missing fields, stage, last contact, consent.
  • Party notification Insurer and loss adjuster notified via webhook; shared milestone status per role.
  • Exception queue Cases >7 days routed to senior review with 24-hour SLA and recommended action.

Testing approach

The workflow runs against bundled synthetic demo data (8 customer requests, 6 leads, 7 policies, 7 M-Pesa transactions, 5 insurer statements, including deliberate edge cases such as an unmatched payment and an expired policy). No real client data is used, no live webhook is executed during the demo, and no credentials are hard-coded — secrets go through n8n’s credential system.

Error handling

  • Gmail sends Use continueErrorOutput — a failed send is logged to the tracker rather than halting the chase.
  • Dashboard fallback The broker dashboard falls back to localStorage-only mode when the n8n webhook is unavailable — the UI keeps working offline.
  • Send errors Logged to the tracker sheet with the failed client and channel for manual follow-up.

Deliverables included

  • Workflow WB-08 Document Chasing Escalation (n8n workflow definition, importable).
  • Dashboard BrokerFlow document-chase dashboard (case create, case list, multi-party milestone tracker, communication history).
  • Client upload Tokenised, mobile-friendly upload page.
